📧 Email Security

Microsoft 365 Anti-Malware:
What Most Tenants Get Wrong

HS
Hossein Sadeghi
Founder · Cyber Harmony Pty Ltd
Microsoft 365 · Defender for Office 365
Originally on LinkedIn

Most Microsoft 365 tenants I audit have anti-malware enabled. Almost none of them have it configured properly. Here's what you're missing — and why it matters.

Out of the Box

First, understand what you actually have

Every Microsoft 365 tenant with cloud mailboxes gets a default anti-malware policy. It applies to everyone, it's always on, and you can't delete it. That's the good news.

The bad news? The defaults are a starting point — not a finish line.

Configuration

What you should actually be configuring

01
Common Attachments Filter
Enable it. Microsoft maintains a list of file types that are almost never legitimate in email — .ace, .apk, .iso, .vhd, and many more. When detected, you have two options: reject with an NDR or quarantine.
💡 Recommend quarantine — it preserves the message for investigation without delivering it.
02
Zero-Hour Auto Purge (ZAP) for Malware
One of the most underrated protections in the stack. ZAP retroactively pulls back emails that were delivered before malware signatures were available — then quarantines them.
💡 Enable it. Full stop.
03
Quarantine Policy
By default, malware detections use AdminOnlyAccessPolicy — meaning recipients get no notification that a message was quarantined. That's actually correct for malware (you don't want end users releasing malware from quarantine).
💡 Make sure your admins are aware of the queue and reviewing it regularly.
04
Admin Notifications
Configure alerts for malware detected from both internal and external senders separately. An internal sender triggering a malware alert is a red flag — it means a device or account may already be compromised.
05
Custom Policies by User Group
The default policy covers everyone, but it's blunt. Build targeted policies for high-risk groups — executives, finance, IT — with stricter settings.
💡 Custom policies apply to inbound email only. Don't forget your default policy covers outbound.
PowerShell

The PowerShell angle

What the portal hides is that every anti-malware policy is actually two objects under the hood — a MalwareFilterPolicy (the settings) and a MalwareFilterRule (who it applies to). When you build these via PowerShell, you manage them separately. This matters if you're deploying at scale or via IaC pipelines.

PowerShell — Stand up a policy with attachments filter + admin notifications
New-MalwareFilterPolicy -Name "Finance Team Policy" \
  -EnableFileFilter $true \
  -EnableInternalSenderAdminNotifications $true \
  -InternalSenderAdminAddress security@yourcompany.com

New-MalwareFilterRule -Name "Finance Team Rule" \
  -MalwareFilterPolicy "Finance Team Policy" \
  -SentToMemberOf "Finance-DL@yourcompany.com"
Testing

Always test your configuration

Microsoft supports the EICAR test file — a harmless 68-byte string that every anti-malware engine treats as malware. Send it as an attachment to a test mailbox and verify it's quarantined, not delivered.

🧪 Test Verification

If the EICAR file arrives in the inbox, your policy isn't working. This test should be part of every new tenant onboarding and policy change validation.

Bottom Line

Anti-malware policies in Defender for Office 365 are not set-and-forget. They require deliberate configuration, regular review, and testing. If you haven't audited yours recently — now is a good time.
